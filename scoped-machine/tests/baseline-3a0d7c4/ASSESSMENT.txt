CONCLUSION

The machine already shares an identical evaluation request, restricts maps
to typed free boundaries, projects faces, interns template instances, and
shares evaluation between checking and ordinary execution. Those mechanisms
are useful and demonstrated. They do not yet implement reuse everywhere an
already established identity, substitution, weakening, or representation
agreement permits it. Eight concrete cases below identify the difference.

The previous handoff made exact reference identity a sufficient sharing key,
but treated it too much as the boundary of sharing. Several conservative
boundaries were prescribed by that handoff; this is not simply a worker
failing to implement it. Runtime identities already act through transport.
The next correction must extend uniform reuse, rather than add a privileged
"learn", "retire", or "install" subsystem from a small example calculus.

MEASURED CASES

1. Construction route.
   Build an application with a variable argument, then specialize it; also
   build the application directly at the specialized argument. Opening gives
   exactly the same tag and fields. The references differ. After the first
   is evaluated, repeating that exact reference launches zero producers;
   requesting the direct construction launches one producer and runs four
   evaluator frames. Conversion subsequently confirms equality.
   Root: term.c origin_intern/make_view/reindex and eval.c entry_intern.
   An origin plus substitution and an independently constructed origin are
   different records even when they open to the same computation.

2. Bound-variable names.
   The two identity functions differing only in bound variable identity are
   definitionally equal. Applying the second after applying the first launches
   two producers and runs five frames. Bound identities are in raw origin keys.
   Root: term.c origin_intern, and the evaluation key.

3. Generic computation followed by specialization.
   Evaluate (lambda x. x) z at a free z, obtaining z. Make the intended image a
   ready as well. Substitute z := a and request the instance. It launches one
   producer and repeats four evaluator frames, including the known beta work.
   Root: reindex produces the correct view but does not specialize the stored
   evaluation fact into a reusable forwarding fact for that view.

4. Stronger face without additional relevant work.
   Evaluate (lambda x. a) (p @ i), whose result is a and which never demands
   its argument. Request the same expression under i=0. It launches one new
   producer and repeats four frames. The argument was never evaluated.
   Root: exact projected-face key uses the term's syntactic dimension support;
   it does not use the completed computation's demonstrated independence.
   This example does NOT justify returning every generic WHNF unchanged under
   restriction: a specialized neutral or Glue head can reduce further.

5. Unrelated global declaration.
   Evaluate a closed application involving only universes and a lambda.
   Register one unrelated opaque global, then demand the unchanged term.
   Three producers launch again and six evaluator frames run.
   Root: every evaluator and checker key includes global_env_version.
   The term has no global dependency. Whole-version invalidation is safe but
   strictly coarser than the mathematical dependency in this example.

6. Identity source name.
   Compile the associativity declaration twice with identical context, face,
   diagrams, evidence and result type, changing only IdentityDecl.id.
   The forward and reverse bodies are exactly the same RefIds. The transform
   records and calls differ. Calling the second after the first performs an
   additional APPLY_TRANSFORM, launches one producer, and runs three evaluator
   frames. The result reference is identical; the body itself is already shared.
   Root: compiler.c record_key includes c->decl.id; generic calls include the
   transform registry id. Source provenance need not duplicate executable work.

7. Accounting reduction repeated in a new operation handle.
   Reduce the same conjunction of twelve named work atoms under the same cost
   model twice. First call: 1,365 operation frames. Second: 965 frames. The
   reduction-result record differs, despite identical mathematical inputs.
   Root: work.c step_reduce/reduction_record key memoization by o->mark and
   allocate a sequence-qualified result. Proof checking also uses per-operation
   marks. Some support, cost and formula operations already use persistent
   memoization; the deficiency is specific, not absence of all work-layer caching.

8. Irrelevant context extension in conversion checking.
   Compare two alpha-equivalent functions, repeat the same request, then repeat
   it in a context extended by an unused variable. The exact repeat creates
   zero claims and consumes one checker budget step. The extension creates two
   claims and consumes two steps, as did the initial request.
   Root: check.c conv_claim includes the complete context without its face,
   rather than a dependency-restricted context or a reusable weakening witness.

WHAT THESE RESULTS ESTABLISH

These are missed-reuse results, not observed wrong answers. Several instances
already share the resulting value or child computations while redoing the
wrapper's work. The reported launch/frame counts make that distinction explicit.
The tests do not establish general Lamping optimality, arbitrary identity
discovery, or a global minimal runtime. They establish specific reusable work
that the current representation or cache protocol separates.

The existing work suite also passes all 198 checks. Therefore the suite and
these observations coexist: passing the current suite is insufficient to
establish the stronger sharing requirement.

THE UNIFORM REUSE LAW

For a completed, witnessed reduction under a typed context and face,

    Gamma; phi |- t reduces to u,

and an admitted map sigma : (Delta; psi) -> (Gamma; phi), retain the shared
derivation and use its specialization to continue from u[sigma] when t[sigma]
is demanded. Do not repeat the derivation from t[sigma]. Observe u[sigma]
further when specialization exposes additional reduction. Restriction to a
stronger face and weakening by unused declarations are particular instances.

For a mathematical identity that is not definitional conversion, reuse the
result through its typed action/transport on the requested observation and
retained residual. Do not erase that action by equating all endpoint handles.
The existing diagram compiler's action remains:

    F_p(r) = d_R(p^{-1} . c_L(r)).

A computed proof p already acts here. Any cached factorization or identity
giving an alternative route is itself reusable mathematical information.
Its action, its substitutions, and any residual evaluation are ordinary work.
No cache-miss theorem search, external plan search, or new phase distinction
is required by this law.

IMPLEMENTATION DIRECTION

A. Preserve occurrence records; share their computation.
   Retain original typing annotations, levels, scopes, faces, and provenance
   so malformed occurrences still fail the existing checks. Do not merely
   delete these fields from RefId keys. Distinct valid occurrence references
   may use a common computational producer through a witnessed view/renaming.
   A provenance label may identify a receipt without identifying the work.
   In particular, replacing the current typed key with an untyped opened-head
   hash would undo earlier correctness fixes and is not the requested change.

B. Extend the existing U/R/D producer protocol to reusable pure operations.
   Successful results belong to their immutable semantic inputs, with the
   actual dependencies included. Consumer handles, scheduling policy, host
   call number, and accounting phase do not define a new pure computation.
   Identical concurrent demands join one running producer. Persistent completed
   results survive the destruction of a caller's operation handle.
   For work reduction use the formula and effective immutable cost-model data;
   for proof checking include the proof and its actual model/boundary premises.
   Per-operation cycle/visited marks can remain traversal state, but must not
   be the only location of completed results.

C. Reuse construction and alpha-equivalence uniformly.
   Direct constructors, VIEW specializations, and TVIEW instantiations need
   compatible computational identities or explicit certified aliases. Binder
   renaming is represented in the view; it must not force independent bodies.
   Do this with existing scope maps and canonical binder structure; preserve
   the fresh-owner guarantees and avoid recursive expansion merely to make a
   cache key. The two forms of an input can remain distinct occurrence records.

D. Store reusable completed reduction facts, not only point answers.
   Keep a shared symbolic derivation/forwarding recipe and its typed domain of
   validity. Reindex and restrict it lazily. A specialized answer may need more
   reduction; the part already established is reused. Start with the direct
   specialization and stronger-face cases above. Further observer-specific
   quotients are justified by their existing factorization witnesses.
   Sharing should not depend on discovering an unrelated normal form or solving
   a new global equivalence problem on each request.

E. Restrict contextual and global dependencies.
   Use the dependency-closed free declarations of the whole judgment, including
   types and required faces, for weakening reuse. Track which immutable global
   declaration/body versions a result actually uses. Changing an opaque symbol
   into a definition changes that symbol's dependency; adding an unrelated
   declaration does not. A conservative whole-signature admission gate may
   still govern admission, without making its administrative version the sole
   identity of every independent computed result. Provisional recursive claims
   must still commit with their validated dependencies.
   Session reset may invalidate host pointers; that is not a mathematical law
   requiring all reusable results to become unrelated in the next session.

F. Share compiled behavior while retaining source provenance separately.
   The two declarations in case 6 have literally identical evidence and bodies.
   They can retain distinct source/certificate receipts while using one action
   producer. This does not authorize merging distinct path proofs merely because
   their endpoints agree. A runtime proof is an ordinary parameter to the same
   construction; a registry entry is an optional executable representation/cache.

G. Keep accounting faithful to the improved sharing.
   Consumers still have their own request/delivery occurrences even when they
   share a producer. Adaptation, lookup and new residual work are charged.
   Registering a macro does not turn its entire internal computation into a
   constant-cost step. Compilation, checking and accounting do not get a free
   pass by running outside the evaluator. In the new work ledger, kernel_calls
   explicitly counts whole calls to checking/reindexing rather than their
   primitive work; that counter alone is not a constant-factor C-cost refinement.
   The necessary refinement is to include that work, or supply a proved bound
   that charges it to already counted bounded work. This assessment has not
   completed a separate full cost-refinement audit.

PROPERTIES THAT MUST SURVIVE THE CHANGE

* All prior structural scope, partial-face, level and boundary rejection tests.
* Simultaneous substitution and its composition law; no accidental capture.
* Proof-relevant transport, including nontrivial loops and retained residuals.
* No unconditional replacement of a face-specific result at a weaker face.
* No publication of provisional typing facts or unresolved cyclic evaluation.
* Unique producers, exactly-once continuation delivery, and sharing of mutable
  execution state rather than races between independently recreated entries.
* Changed real dependencies cause recomputation or a witnessed transport;
  unrelated administrative changes do not erase reuse.

These are the meaningful distinctions. Source labels, caller identity,
phase names, harmless renaming, and unused context declarations must not
become unexamined barriers to sharing.
