## Key Question 1: Which repos exist, who owns them, what language, how big, when active?

### Takeaway
The canonical implementation is `zippy/ceptr`, a ~17.8k-line C codebase with 990 commits, almost entirely written by Eric Harris-Braun between Feb 2013 and Jul 2016, then dormant until a three-line "fix compile" commit in Feb 2026 that immediately preceded two new AI-era ports (`zippy/ceptr-rs`, `zippy/ceptr-js`). Earlier prototypes were in Clojure (`zippy/anansi`, 2011) and in a C "periodic_table" experiment archived inside the main repo; there is no Ruby/Python/CoffeeScript Ceptr prototype and no package on npm, RubyGems or crates.io.

## Key Question 2: What does the C implementation actually implement end-to-end?

### Takeaway
The C codebase implements, with tests, every named design concept at the library level — semantic trees, semtrex matching/parsing, receptors with expectations/signals, a run-tree process reducer with ~59 system processes, protocols with role expression/unwrapping, scapes, a VMHost with threads, streams/sockets, an instance "accumulator", and a tiny shell — but the end-to-end composition (a running node with HTTP edge receptor) was still "in progress" when work stopped, and the 2026 port analysis describes system-level fidelity as never having been composed end-to-end.

### Cited Findings

- README: `make ceptr` builds "a ceptr node running the command-line receptor, which is currently very primitive, with just four commands" (time, receptors, debug, quit) — [README](https://github.com/zippy/ceptr/blob/master/README.md)
- `contexts/INTERNET.cptr` (29 lines) is loaded at boot (`load_contexts(G_sem)`) and defines an `echo2stream` process (STREAM_WRITE + TRANSCODE to LINES) in a STREAM_EDGE context and an `HTTP` protocol in an INTERNET context built by INCLUSION of `REQUESTING` with roles HTTP_CLIENT/HTTP_SERVER and symbols HTTP_REQUEST/HTTP_RESPONSE on HTTP_ASPECT — [INTERNET.cptr](https://github.com/zippy/ceptr/blob/master/contexts/INTERNET.cptr)

### Inferences
- Concept coverage: semantic trees, semtrex, receptors/expectations/signals, processes (run-tree reduction with ~59 system instructions), protocols (definition, inclusion/unwrapping, role expression, initiation), scapes (minimal, 93 lines), VMHost (threads, routing, clock), streams and TCP sockets (listener on 8888), and an instance store are all implemented in C. "Holographic storage"/multi-instance replication (the part that became Holochain) is not implemented here beyond issue #94.
- The HTTP edge receptor is wired in `main()` but the related issues were still "in progress"/"partial" in mid-2016, so the HTTP path should be regarded as demo-grade.

## Key Question 3: How does the test suite work and what does it demonstrate?

### Takeaway
Tests are a single C executable (`ceptr_specs`) built by `make test`, composed of 17 `spec/*_spec.h` headers included into `spec/ceptr_specs.c`; a 43-line macro framework (`spec_is_equal`, `spec_is_str_equal`, …) counts passes/failures and prints a dot-per-assertion report. Statically there are 182 test functions and 1,098 assertions, and the specs double as Doxygen examples; the richest ones (`process_spec.h`, `semtrex_spec.h`, `tree_spec.h`, `receptor_spec.h`) demonstrate run-tree reduction, tree matching, and the full REQUESTING/RECOGNIZE protocol signal cycle.

### Cited Findings
- Makefile: `ceptr: gcc -fcommon -pthread -g -o ceptr $(CEPTR_SRC_FILES)`; `test: ceptr_specs` then `./ceptr_specs`; `ceptr_specs` compiles all `src/*.c` (minus `ceptr.c`) plus `spec/*.c`; `clean` removes binaries; the `base_defs.pl` regeneration rule is commented out — [Makefile](https://github.com/zippy/ceptr/blob/master/Makefile)
- README: "To compile and run all the tests simply … type: make test. This runs all of the tests, which live in the specs sub-directory." and "We use test driven development … Our testing framework provides a bunch of C macros that test an expectation with a result" — [README](https://github.com/zippy/ceptr/blob/master/README.md)
- `spec/test_framework.h` (43 lines) defines `spec_is_true/false/equal/str_equal/long_equal/ptr_equal/path_equal/float_equal/buffer_equal`, each incrementing `spec_total`, printing `.` or `F`, storing a failure string (max 1000), and `report_tests()` prints "All %d specs pass" or lists failures — [test_framework.h](https://github.com/zippy/ceptr/blob/master/spec/test_framework.h)

## Key Question 5: Code examples showing how to define a receptor or protocol

### Takeaway
There are no tutorial-style examples in the README ("Usage: TBD"), but the spec files and `contexts/INTERNET.cptr` contain concrete, runnable definitions: receptor symbol/structure definitions via `_r_define_symbol`/`_r_define_structure`, protocol definitions as PROTOCOL_DEFINITION trees (REQUESTING, RECOGNIZE, HTTP) built by INCLUSION/LINKAGE/RESOLUTION, role expression via `_o_express_role`, and the shell's `addCommand`.
