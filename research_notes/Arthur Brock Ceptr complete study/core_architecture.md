## Key Question 1: What is the exact definition and structure of a semantic tree, and why did Ceptr claim this replaces both types and formats?

### Takeaway
A semantic tree is an ordered tree in which every node carries a `SemanticID` ("Symbol": what the data means) plus a raw "surface" (bytes) whose layout is given by the Symbol's declared "Structure"; Symbols and Structures alternate recursively (a Structure is itself a composition of Symbols) down to a small set of system "bottoming-out" structures (BIT, INTEGER, FLOAT, CSTRING, ...). Because meaning and structure travel with the data, Ceptr argued there is no separate type system (compile-time) and no separate wire format/schema (XML/JSON + parser) — the same tree is the type, the format, the storage layout, and (for code) the program.

### Cited Findings
- Doxygen group docs: "Semantic trees are the basic data building block for ceptr. Everything in ceptr is built out of semantic trees. In ceptr all data is assumed to be meaningfull, not just structured." — [tree.h](https://github.com/zippy/ceptr/blob/master/src/tree.h)
- "The basic structure of memory in Ceptr is semantic trees. This means you cannot store just an integer, but a semantic use of the integer (specifying what it MEANS) such as a street address, age, or shoe size." Code is "built on these basic DEFINITIONS of STRUCTURES (like Integer, Float, Boolean -- how to interpret a series of bits) and SYMBOLS (like age, address, hair color -- the meaning of the structure)." — [doxy/main.dox](https://github.com/zippy/ceptr/blob/master/doxy/main.dox) / [zippy.github.io/ceptr](http://zippy.github.io/ceptr/)
- Definition module docstring: "Structures are definitons of how data is organized; Symbols are a numeric semantic indicator (like a type) of what a given structure means. For example an 'integer' defines a structures of bits and how to interpret them, whereas a 'shoe size' is a symbol for what a use of an integer means." — [def.h](https://github.com/zippy/ceptr/blob/master/src/def.h)
- Exact C node layout (pointer implementation): `struct T { Tstruct structure; Tcontext context; Tcontents contents; }` where `Tstruct = {uint32_t child_count; T *parent; T **children}`, `Tcontext = {uint32_t flags}`, `Tcontents = {Symbol symbol; size_t size; void *surface}`. Run-tree nodes `rT` append `uint32_t cur_child`. Surface flags include `TFLAG_SURFACE_IS_TREE`, `TFLAG_SURFACE_IS_RECEPTOR`, `TFLAG_SURFACE_IS_SCAPE`, `TFLAG_SURFACE_IS_CPTR`, `TFLAG_RUN_NODE`. — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h), [tree.h](https://github.com/zippy/ceptr/blob/master/src/tree.h)
- Exact SemanticID: `typedef struct SemanticID { Context context; /*uint32_t, "4G types of receptors"*/ SemanticType semtype; /*uint16_t*/ SemanticAddr id; /*uint16_t, "64K types of symbols/structure per receptor"*/ }`; `enum SemanticTypes {SEM_TYPE_STRUCTURE=1, SEM_TYPE_SYMBOL, SEM_TYPE_PROCESS, SEM_TYPE_RECEPTOR, SEM_TYPE_PROTOCOL}`; aliases `typedef SemanticID Symbol, Structure, Process, Protocol, Recept`. A comment notes the enum values "must match the order they show up in the definition trees". — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h)
- Contexts: a `SemTable` holds up to `MAX_CONTEXTS 100` `ContextStore`s, each a `T *definitions` tree; a receptor's definitions create a context ("Context parent; the context this receptor's definition lives in; Context context; the context this receptor's definition creates"). The semtable "coordinat[es] meaning across a vmhost". — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h), [semtable.h](https://github.com/zippy/ceptr/blob/master/src/semtable.h)
- The definitions tree itself is a semantic tree: `Symbol: DEFINITIONS,[(STRUCTURES,SYMBOLS,PROCESSES,PROTOCOLS,RECEPTORS,*SCAPES)]`; `SYMBOL_DEFINITION = (SYMBOL_LABEL, SYMBOL_STRUCTURE)`; `STRUCTURE_DEFINITION = (STRUCTURE_LABEL, STRUCTURE_DEF)`; `STRUCTURE_DEF` is one of `STRUCTURE_SYMBOL | STRUCTURE_SEQUENCE | STRUCTURE_OR | STRUCTURE_ZERO_OR_MORE | STRUCTURE_ONE_OR_MORE | STRUCTURE_ZERO_OR_ONE | STRUCTURE_STRUCTURE | STRUCTURE_ANYTHING`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Structure-definition grammar in the `base_defs` DSL: `(x,y...)` sequence, `?x` zero-or-one, `*x` zero-or-more, `+x` one-or-more, `|{x|y}` logical or, `%x` "symbol of given structure", `!` anything. Doxygen key: "SEQ = Sequence of, * = zero or more, + = one or more, ? zero or one, OR = logical or, % = symbol of given structure, ! = any symbol." — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs), [sys_defs.dox](https://github.com/zippy/ceptr/blob/master/doxy/sys_defs.dox)
- Bottoming-out system structures (defined with `NULL_SYMBOL` "because it's not really defined in ceptr terms"): `BIT, INTEGER (c int), INTEGER64, FLOAT, CHAR, CSTRING, SYMBOL, STRUCTURE, PROCESS, PROTOCOL, RECEPTOR (surface is a SemID), SCAPE, ENUM (@todo), TREE_PATH (-1 terminated ints), XADDR, SURFACE, TREE (c pointer to a tree, "orthogonal tree"), RECEPTOR_SURFACE, SEMTREX, CPOINTER (edge receptor data), UUID, BLOB`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Example of the alternation: `Symbol: YEAR,INTEGER; ... Structure: DATE,YEAR,MONTH,DAY; Structure: TIME,HOUR,MINUTE,SECOND; Symbol: TODAY,DATE; Symbol: NOW,TIME; Structure: TIMESTAMP,TODAY,NOW; Symbol: TICK,TIMESTAMP;` — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Labels: "Label tables map human readable text strings to parts of semantic trees ... used to provide human readable references for symbols, structures, processes (including locals/parameter references in process code)". Labels are themselves typed symbols (`ENGLISH_LABEL, SPANISH_LABEL, FRENCH_LABEL, GERMAN_LABEL` all CSTRING; also domain labels like `HTTP_HEADER_LABEL` with `Label: CONTENT_TYPE,HTTP_HEADER_LABEL,"Content-Type"`), and `GET_LABEL` is a VM instruction. — [label.h](https://github.com/zippy/ceptr/blob/master/src/label.h), [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Textual/lisp-like notation used throughout for trees: `(SYMBOL:value)` for leaves and `(SYMBOL (child) (child))` for branches, e.g. `(HEAD (FROM_ADDRESS (RECEPTOR_ADDR:3)) (TO_ADDRESS (RECEPTOR_ADDR:3)) (ASPECT_IDENT:DEFAULT_ASPECT) (CARRIER:backnforth))`; `_t_parse()` parses it and `_t2s()` prints it. — [protocol_spec.h](https://github.com/zippy/ceptr/blob/master/spec/protocol_spec.h), [tree.h](https://github.com/zippy/ceptr/blob/master/src/tree.h)
- A second, cache-friendly "matrix tree" implementation (`M`/`L`/`N` structs, levels of node arrays, `Maddr {level,index}`, `H` handles) exists alongside the pointer tree, with serialization offsets (`SERIALIZED_NODE_SIZE` etc.). — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h), [mtree.h](https://github.com/zippy/ceptr/blob/master/src/mtree.h)
- Tree hashing (`TreeHash _t_hash`), serialization (`_t_serialize/_t_unserialize`), JSON dump (`_t2json`) and template filling (`_t_fill_template`) are tree-level primitives. — [tree.h](https://github.com/zippy/ceptr/blob/master/src/tree.h)
- Claim against "words": "The fundamental data unit in Ceptr is not a 32 or 64 bit word; it's a semantic tree." and "Ceptr programs are just another type of semantic tree." (homoiconic). — [ceptr.org/projects/core](http://ceptr.org/projects/core)
- Claim against formats: messages are semantic trees where "each node carries a symbol identifier"; "Unlike XML or JSON text labels, the page uses semantic IDs that point to a complete semantic definition covering data type, structure, and special operators"; semantic trees are "the base data structure for all memory in the virtual machine." — [ceptr.org/projects/pcubed](http://ceptr.org/projects/pcubed)
- Revelation: semantics built into base structure — you "Cannot create an instance of an Int, but can of an Age." — [ceptr.org/whitepapers/revelation](http://ceptr.org/whitepapers/revelation)
- Semtrex Intro article: "data always carries with it its semantics" and "the meaning (semantics) of something is very naturally expressed as tree structures"; the SMTP example: "we strip off the structure and semantic meaning and in fact store and transmit the email address with none of its original structure"; Brock quoted: when compiled, meaning "all goes away, collapsed down to structured data in memory addresses ... we have to then construct a semantic layer where we 'hydrate' the meaning back". Harris-Braun quoted: "Meaning comes from having a social context in which symbols are applied to embodied forms (structures!)". — [Semtrex Intro article](https://github.com/zippy/ceptr/blob/master/articles/Semtrex%20Intro/semtrex%20intro.htm)
- Slide deck: "In Ceptr, Everything is stored as Semantic Trees". — [Prezi: Just a Spoonful of Ceptr](https://prezi.com/y_7109dt0gzj/just-a-spoonful-of-ceptr/)
- Grammatics whitepaper describes semantic trees as "formalizations of meaning, where meaning comes from process" and notes "Semantic alternation between Symbols and Structures". — [ceptr.org/whitepapers/grammatics](http://ceptr.org/whitepapers/grammatics)
- Structural validation: `_d_build_def_semtrex()` / `_r_build_def_semtrex()` compile a Symbol's Structure definition into a Semtrex, and `_r_def_match()` checks an instance tree against it (used e.g. in `http_example.h`: "confirm that we built the request right!"). — [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h), [http_example.h](https://github.com/zippy/ceptr/blob/master/spec/http_example.h)

### Inferences
- "Replaces types": a Symbol is a globally identifiable (context, semtype, id) tag; its Structure plays the role of a type definition, but the definition lives in a runtime semantic tree (introspectable, serializable, versionable per context) rather than a compiler's symbol table. Type-checking at runtime is done by Semtrex matching against the structure definition (`_r_def_match`).
- "Replaces formats": since every value is self-describing, serialization is a mechanical walk (`_t_serialize`), and parsing untyped input (bytes/ASCII) is pushed to the "edge" where a Semtrex "embodies" a semantic tree from an `ASCII_CHARS` tree (see Q3). Inside, no format negotiation is needed — "Semantic coherence" between parties reduces to sharing definitions (contexts).
- The 16-bit `SemanticAddr` and 32-bit `Context` are prototype limits, not design limits (the docs elsewhere speak of UUID-sized identifiers for compository/CeptrNet).

### Gaps
- The 2015 ceptr.org blog post "Semantic Trees" (which the Semtrex article calls "a good blog post (including a couple videos!)") could not be retrieved (Wayback blocked); its exact wording of the "types and formats" claim is unverified.
- No formal written specification of the semantic-tree model beyond the code and the draft whitepapers was found.

## Key Question 2: What is a receptor, what state does it hold, and what are its lifecycle operations?

### Takeaway
In the implementation a receptor is a `RECEPTOR_INSTANCE` semantic tree (plus a C struct for fast access) that owns: its own semantic context (definitions of symbols/structures/processes/protocols), an instance store addressed by `Xaddr`, a "flux" of aspects each holding expectations (Semtrex listeners) and received signals, pending outbound signals/responses, conversations, and a process queue. Lifecycle = define/new → add expectations (directly or by "expressing a role" in a protocol) → activate in a VMHost → receive/deliver signals → reduce run-trees → send → serialize/sleep → free/kill. The conceptual layer (membranes, fractal nesting, multi-instance holographic storage) is mostly on paper.

### Cited Findings
- Conceptual: "A Receptor is a lightweight virtual machine. Receptors can contain other receptors, which is what enables the fractal layers of computing". Receptors "run processes" and "store information"; "You can select holographic storage mechanisms which use cryptographic structures (such as hash chains and merkle trees)". — [doxy/main.dox](https://github.com/zippy/ceptr/blob/master/doxy/main.dox)
- "Receptors provide the fundamental coherence contexts for ceptr". — [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h)
- "A running receptor is always instantiated in the (address) space of another receptor." The VMhost "hosts all receptors as peers, with communication constrained by the hierarchy." — [ceptr.org/projects/core](http://ceptr.org/projects/core)
- Slide deck: "Composable units for computing and communication"; "Receptors have membranes, and are organized fractally"; receptors "Manage their membranes ( in / out / transforms )"; "Bound to external carrier(s) ... upon instantiation (like lock & key in hormones)"; compared to a function call ("what-is-my-location", "filter-list"). — [Prezi](https://prezi.com/y_7109dt0gzj/just-a-spoonful-of-ceptr/)
- Exact C struct: `struct Receptor { T *root; /*RECEPTOR_INSTANCE tree*/ Context parent; Context context; ReceptorAddress addr; SemTable *sem; T *flux; T *pending_signals; T *pending_responses; T *conversations; pthread_mutex_t pending_signals_mutex, pending_responses_mutex; Instances instances; Q *q; /*process queue*/ int state; /*Alive=0,Dead*/ T *edge; /*data store for edge receptors*/ }`. Comment: "A Receptor is a semantic tree, pointed to by root, but we also create c struct for faster access". — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h)
- Tree form: `RECEPTOR_INSTANCE = (INSTANCE_OF, CONTEXT_NUM, PARENT_CONTEXT_NUM, RECEPTOR_STATE)`; `RECEPTOR_STATE = (FLUX, PENDING_SIGNALS, PENDING_RESPONSES, CONVERSATIONS, RECEPTOR_ELAPSED_TIME)`; `FLUX = [+%ASPECT]` ("tree to hold all incoming and in process signals on the various aspects"); `Structure: ASPECT,(EXPECTATIONS,SIGNALS)`; `Symbol: DEFAULT_ASPECT,ASPECT`; `RECEPTOR_DEFINITION = (RECEPTOR_LABEL, DEFINITIONS)`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Aspects: `enum AspectType {EXTERNAL_ASPECT=0, INTERNAL_ASPECT}` with comment "aspects appear on either side of the membrane"; `typedef Symbol Aspect` ("aspects are identified by a semantic Symbol identifier"); `ASPECT_DEF = (ASPECT_TYPE /*BIT, "really should be an enum of IN, OUT"*/, ASPECT_LABEL)`. — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h), [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Expectations (listeners): `EXPECTATION = (CARRIER, PATTERN, ACTION, PARAMS, END_CONDITIONS, ?SEMANTIC_MAP, ?CONVERSATION_UUID)`; `PATTERN,SEMTREX_DEF` ("expectation is a semtrex"); `ACTION,PROCESS`; `END_CONDITIONS = (?TIMEOUT_AT, ?REPETITIONS)` with `REPETITIONS = COUNT | UNLIMITED`. Built by `_r_add_expectation(Receptor*, Aspect, Symbol carrier, T *pattern, T *action, T *with, T *until, T *using, T *cid)`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs), [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h)
- Creation: `_r_new(SemTable*, SemanticID r)` builds `(RECEPTOR_INSTANCE (INSTANCE_OF:r) (CONTEXT_NUM:...) (PARENT_CONTEXT_NUM:...) state)`; the SYS_RECEPTOR gets context 0 / parent -1. Definition helpers: `_r_define_symbol`, `_r_define_structure`, `_r_define_process(r, code, name, intention, signature, link)`, `_r_define_protocol`. — [receptor.c](https://github.com/zippy/ceptr/blob/master/src/receptor.c), [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h)
- Instance store: `Xaddr {Symbol symbol; int addr}` ("An eXistence Address consists of the semantic type (Symbol) and an address"); `_r_new_instance`, `_r_get_instance`, `_r_set_instance`, `_r_delete_instance`, `_r_hash`, delegated to the accumulator (`_a_new_instance` etc.); instances live in an `INSTANCE_STORE = (INSTANCES, ?INSTANCE_TOKENS)` tree with `INSTANCE_TOKEN` "to refer to an xaddr from outside the receptor". VM instructions `NEW`, `GET`, `DEL` operate on these. — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h), [accumulator.h](https://github.com/zippy/ceptr/blob/master/src/accumulator.h), [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Signaling ops: `__r_make_signal(from,to,aspect,carrier,contents,in_response_to,until,conversation)`, `_r_send`, `_r_request(r,signal,response_carrier,code_point,process_id,cid)` (records a `PENDING_RESPONSE = (SIGNAL_UUID, CARRIER, WAKEUP_REFERENCE, END_CONDITIONS, ?CONVERSATION_IDENT)` and raises an error if "request missing END_CONDITIONS"), `_r_deliver`, `__r_test_expectation`, conversation helpers `_r_add_conversation/_r_find_conversation/__r_cleanup_conversation`. — [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h), [receptor.c](https://github.com/zippy/ceptr/blob/master/src/receptor.c)
- Serialization/sleep: `_r_serialize(Receptor*, void**, size_t*)` / `_r_unserialize(SemTable*, void*)`; `SERIALIZED_RECEPTOR,BLOB`. The VMhost "can serialize receptors to disk to put them to sleep, and wake them back into memory." — [receptor.h](https://github.com/zippy/ceptr/blob/master/src/receptor.h), [ceptr.org/projects/core](http://ceptr.org/projects/core)
- Install/package model: `RECEPTOR_PACKAGE = (MANIFEST, RECEPTOR_IDENTIFIER, DEFINITIONS)`; `MANIFEST = [+MANIFEST_PAIR(MANIFEST_LABEL, MANIFEST_SPEC)]` ("configuration template to be filled out for the installation of a receptor"); `BINDINGS = [+BINDING_PAIR(MANIFEST_LABEL, !)]`. But `_v_load_receptor_package` and `_v_install_r` both begin with `raise_error("not implemented")`, and `_r_new_receptor_from_package` raises "fix receptor address". The VMHost keeps `Scape *installed_receptors` keyed by hash of the package id. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs), [vmhost.c](https://github.com/zippy/ceptr/blob/master/src/vmhost.c), [receptor.c](https://github.com/zippy/ceptr/blob/master/src/receptor.c)
- Activation in a host: `_v_new_receptor(VMHost*, Receptor *parent, Symbol s, Receptor *r)` returns an Xaddr; `_v_activate(v, x)` puts it in `active_receptors`; `__r_kill(r)` on shutdown; `_r_free`. - Each receptor's definitions form a semantic context; in `sys_defs.c` a context named in a `.cptr` file is created as `(RECEPTOR_DEFINITION (RECEPTOR_LABEL %) (DEFINITIONS (STRUCTURES) (SYMBOLS) (PROCESSES) (RECEPTORS) (PROTOCOLS) (SCAPES)))` via `__d_define_receptor`, and code chunks are reduced inside a temporary receptor of that context. Contexts defined in `base_defs`: `SYS, COMPOSITORY, DEV_COMPOSITORY, TEST, CLOCK, STREAM_EDGE, INTERNET`. — [sys_defs.c](https://github.com/zippy/ceptr/blob/master/src/sys_defs.c), [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Membranes on paper only: Revelation says "With proper coherence & membranes, privacy becomes an issue of configuration" but does not define them; the README uses "membrane" socially ("each membrane within our social organism"). — [ceptr.org/whitepapers/revelation](http://ceptr.org/whitepapers/revelation), [README](https://github.com/zippy/ceptr)
- Multi-instance/holographic receptors: the README states this piece ("synchronization for multi-instance receptors") was "pulled out" and became Holochain; Ceptr Core page: C codebase "being retired", to be rebuilt in Go after Holochain launches. — [README](https://github.com/zippy/ceptr), [ceptr.org/projects/core](http://ceptr.org/projects/core)

### Inferences
- The implemented "membrane" is the aspect/flux structure: signals addressed to an aspect are appended to that aspect's SIGNALS list and tested against that aspect's EXPECTATIONS; the `EXTERNAL_ASPECT/INTERNAL_ASPECT` enum is the only trace of a two-sided membrane in code.
- Receptor nesting is implemented only as (a) definition contexts nested by parent context and (b) a flat VMHost routing table; there is no address-space containment of child receptors at runtime.

### Gaps
- No implemented code for receptor cloning across hosts, sharding, or hash-chain storage was found in this repo (that work moved to Holochain).
- The "Fractal Virtual Machine" whitepaper page is a title-only stub.

## Key Question 3: How does Semtrex work, with examples of its syntax?

### Takeaway
Semtrex (Semantic Tree Regular Expressions) is a pattern language over semantic trees: a Semtrex is itself a semantic tree (`SEMTREX_*` symbols), has a linear text syntax with a BNF, is compiled into a Thompson/Russ-Cox-style NFA whose transitions are *tree moves* (next sibling, descend, pop N levels) instead of "next character", matches on Symbol identity and/or surface value, and returns a match-result tree with named capture groups from which a new semantic tree can be "embodied".

### Cited Findings
- "Semtrex provides a language for pattern matching on semantic trees similar to regular expressions for matching on text strings." "A Semtrex is itself a semantic tree, but we have also created a linear textual representation of (and parser for) semtrex trees". — [semtrex.h](https://github.com/zippy/ceptr/blob/master/src/semtrex.h), [doxy/semtrex.dox](https://github.com/zippy/ceptr/blob/master/doxy/semtrex.dox)
- Official BNF (verbatim from `doxy/semtrex.dox`):
  ```
  <semtrex>        ::= <root> [ "/" <child>...]
  <root>           ::= "/" <element>
  <child>          ::= <element> | <optional> | <semtrex>
  <element>        ::= <walk> | <symbol_literal> | <value_literal> | <symbol_literal_set> | <value_literal_set> | <any> | <capture> | <siblings>
  <optional>       ::= <or> | <zero_or_more> | <one_or_more> | <zero_or_one>
  <walk>           ::= "%" <semtrex>
  <one_or_more>    ::= <semtrex> "+"
  <zero_or_more>   ::= <semtrex> "*"
  <zero_or_one>    ::= <semtrex> "?"
  <sequence>       ::= <semtrex> ["," <semtrex>]...
  <siblings>       ::= "(" <sequence> ")"
  <or>             ::= <semtrex> "|" <semtrex>
  <symbol_literal> ::= ["!"] <symbol>
  <symbol_literal_set> ::= ["!"] "{" <symbol> ["," <symbol>]... "}"
  <value>          ::= <string> | <char> | Int | Fload
  <value_literal>  ::= <symbol> ["!"] "=" <value>
  <value_literal_set> ::= <symbol> ["!"] "={" <value> ["," <value> ]... "}"
  <any>            ::= "."
  <capture>        ::= "<" <symbol> ":" <semtrex> ">"
  ```
  — [doxy/semtrex.dox](https://github.com/zippy/ceptr/blob/master/doxy/semtrex.dox)
- Semtrex tree node types: `SEMTREX_SYMBOL_LITERAL` ("matches on the semantic type"), `SEMTREX_SYMBOL_LITERAL_NOT`, `SEMTREX_SEQUENCE` ("Ex: comma separated nodes"), `SEMTREX_OR`, `SEMTREX_NOT` ("Ex: ~ (not implemented)"), `SEMTREX_SYMBOL_ANY` ("Ex: ."), `SEMTREX_ZERO_OR_MORE` ("Ex: /0/TestSemtrex*"), `SEMTREX_ONE_OR_MORE`, `SEMTREX_ZERO_OR_ONE`, `SEMTREX_VALUE_LITERAL` ("Matches on the semantic type and the data values"), `SEMTREX_VALUE_LITERAL_NOT`, `SEMTREX_GROUP` ("Ex: <...>operator"), `SEMTREX_WALK`, `SEMTREX_DESCEND`. Match results: `SEMTREX_MATCH` (root surface = group id) with children `SEMTREX_MATCH_SYMBOL`, `SEMTREX_MATCH_PATH` (a TREE_PATH), `SEMTREX_MATCH_SIBLINGS_COUNT` ("the length of the match") and nested `SEMTREX_MATCH`es. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Engine: "The code to generate finite state automata to match the trees is based heavily on Russ Cox's great work" (cox2007.pdf is in `articles/`). - API: `parseSemtrex(sem, "...")` → tree; `_t_match(semtrex, t)` → bool; `_t_matchr(semtrex, t, &results)` → bool + match tree; `_t_get_match(result, group)`; `_t_embody_from_match(sem, match, group, t)` builds a new semantic tree from captures; `_stx_replace(semtrex, t, replace)`; `_dump_semtrex` prints text form; `makeASCIITree("...")` wraps a C string as `(ASCII_CHARS (ASCII_CHAR:'c')...)`; `_stx_results2sem_map` turns match results into a `SEMANTIC_MAP`. - Worked example from the Semtrex Intro article: input string `42.25,73.25` → ASCII tree; expression `/ASCII_CHARS/<HomeLocation:<lat:ASCII_CHAR+>,ASCII_CHAR=',',<lon:ASCII_CHAR+>>`; "The angle brackets indicate that we are on the fly naming (or assigning a semantic symbol) the matching part"; match result `(SEMTREX_MATCH:1 (SEMTREX_MATCH_SYMBOL:HomeLocation) (SEMTREX_MATCH_PATH:/1) (SEMTREX_MATCH_SIBLINGS_COUNT:11) (SEMTREX_MATCH:3 (SEMTREX_MATCH_SYMBOL:lat) (SEMTREX_MATCH_PATH:/1) (SEMTREX_MATCH_SIBLINGS_COUNT:5)) (SEMTREX_MATCH:2 (SEMTREX_MATCH_SYMBOL:lon) (SEMTREX_MATCH_PATH:/7) ...))`; then "Embody" yields a `HomeLocation` tree with `lat`/`lon` floats; and `/%HomeLocation/(lat=42.25,lon=73.25)` (the `%` walk operator searching anywhere in the tree) matches the embodied tree. "inputs are semantic trees, expressions are semantic trees, and Semtrex matches input trees against expression trees. In fact, all output from Semtrex is a semantic tree as well." — [Semtrex Intro article](https://github.com/zippy/ceptr/blob/master/articles/Semtrex%20Intro/semtrex%20intro.htm)
- Difference from regex (article): "Semtrex matches on the semantics of the data as well as literal values, whereas Regex, having no concept of the semantics on which it is matching, can match only on the literal values"; "42 years old" does not match "42 is the answer..." — [Semtrex Intro article](https://github.com/zippy/ceptr/blob/master/articles/Semtrex%20Intro/semtrex%20intro.htm)
- Revelation gives the illustrative path-style example `/HTTP_REQUEST/*/HOST="ceptr.org"` (matching "by semantic ID, value, or tree position"). — [ceptr.org/whitepapers/revelation](http://ceptr.org/whitepapers/revelation)
- Slide deck: Semtrex = "General Pattern Parser", "rendered in ASCII format", supports a "Self-Describing Protocol Stack". — [Prezi](https://prezi.com/y_7109dt0gzj/just-a-spoonful-of-ceptr/)
- Semtrex is also used internally as the "universal parser": the Semtrex text parser itself tokenizes to an `STX_TOKENS` tree and uses Semtrex (`/STX_TOKENS/(%<SEMTREX_SEQUENCE:(!STX_COMMA,STX_COMMA)+,!STX_COMMA>)`) to build the expression tree; the `_t_parse` tree parser likewise tokenizes to `P_TOKENS`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs), [semtrex_spec.h](https://github.com/zippy/ceptr/blob/master/spec/semtrex_spec.h)

### Inferences
- Semtrex plays three roles: (1) structural validation (structure defs compile to Semtrex), (2) expectation/listener matching inside receptors, and (3) edge parsing of byte streams into semantic trees via capture groups + embodiment. This is what "universal parsing system" on ceptr.org means concretely.
- Captures are not substrings but *named subtrees* whose capture symbol becomes the Symbol of the embodied node — so parsing and typing happen in one step.

### Gaps
- `SEMTREX_NOT` (`~`) is declared but marked "not implemented"; the `<walk>` and `<descend>` semantics are documented only in code.
- No performance analysis or formal semantics of the tree-FSA was found.

## Key Question 4: How does Ceptr's protocol system work (protocol definition, binding, "wrapping" protocols), and what did "pluggable protocols" mean concretely?

### Takeaway
A Ceptr protocol is an executable semantic tree (`PROTOCOL_DEFINITION`) consisting of abstract semantic references — ROLEs (agents), GOALs (processes), USAGEs (symbols), WEALs (sub-protocols) — plus one or more INTERACTIONs made of `EXPECT` (role R, from role S, Semtrex pattern, action) and `INITIATE` (role, destination role, action) clauses. "Pluggable" means the abstract slots are bound at install/express time: a receptor "expresses a role" by supplying `PROTOCOL_BINDINGS` (RESOLUTIONs mapping GOAL→ACTUAL_PROCESS, ROLE→ACTUAL_RECEPTOR, USAGE→ACTUAL_SYMBOL, etc.), which installs the role's EXPECTs as expectations on an aspect. "Wrapping" is `INCLUSION`: a new protocol includes another by name (`PNAME`) and LINKs/RESOLVEs its references (e.g. `RECOGNIZE` wraps the abstract `REQUESTING`). This was built and tested in C; transformational maps and front-end-protocol transcoding were only partially done.

### Cited Findings
- Design statement: a Protocol is "live, executable, component, not an RFC paper"; "what is typically called a 'protocol' in a specification is for us an EMPTY protocol template whose connection points must be bound when it is installed"; slot types "CONNECTION: an endpoint binding for the protocol", "ROLE: the RECEPTOR_ADDRESS of an agent", "GOAL: a PROCESS to be run", "USAGE: semantic data passed in the signal". Composability: chaining through endpoints, nesting ("a whole protocol placed in a content slot"), extending. Match triggers: "Expect On <carrier> Match <semtrex-expr> Do <script> [With <parameters>]". Transformational maps (direct, combined, computed, dropped, merged) — "The map transformer is not yet built." "The protocol was built and prototyped in the C implementation of Ceptr and is being reimplemented in Go." — [ceptr.org/projects/pcubed](http://ceptr.org/projects/pcubed)
- Front-end vs back-end: "Front-end protocols are 'customizable, programmable ways to send communications in various formats'" (HTTP, SMTP, FTP); back-end protocols "built into Ceptr for internal functions like synchronization, verification, and mirroring"; "Every message is a Ceptr style message which just identifies the different protocol it's using semantically." — [ceptr.org/projects/core](http://ceptr.org/projects/core)
- Slide deck: "Ceptr protocols are pluggable / fully functional"; expectation form "ON <carrier> EXPECT <semtrex_pattern> DO <action>". Revelation: expectations "ON EXPECT [DO] [WITH] [UNTIL]", bindable to receptor aspects "or planted as remote listeners in other receptors". — [Prezi](https://prezi.com/y_7109dt0gzj/just-a-spoonful-of-ceptr/), [ceptr.org/whitepapers/revelation](http://ceptr.org/whitepapers/revelation)
- Exact definition grammar: `PROTOCOL_DEFINITION = (PROTOCOL_LABEL, PROTOCOL_SEMANTICS, *PROTOCOL_DEFAULTS, *%INTERACTION, *INCLUSION)`; `PROTOCOL_SEMANTICS = (*ROLE, *GOAL, *USAGE, *WEAL)`; `Structure: INTERACTION,(*EXPECT,*INITIATE)`; `EXPECT = (ROLE, SOURCE[+ROLE], PATTERN, ACTION, ?PARAMS)`; `INITIATE = (ROLE, DESTINATION[+ROLE], ACTION)`; `INCLUSION = (PNAME, +(RESOLUTION|LINKAGE))`; `Structure: MAPPING,|{WHICH_PROCESS|WHICH_RECEPTOR|WHICH_SYMBOL|WHICH_PROTOCOL|WHICH_VALUE}` ("maps abstract semantic reference to concrete instantiation"), `RESOLUTION,MAPPING`; `Structure: LINK,|{WHICH_GOAL|WHICH_ROLE|WHICH_USAGE|WHICH_WEAL}` ("links two abstract semantic references"), `LINKAGE,LINK`; `PROTOCOL_BINDINGS = [+RESOLUTION]`. Semantic references: "A role stands for an expected agent", "A goal stands for an intended process", "A usage stands for a(n) X of a Symbol", "A weal stands for a included protocol". — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- Slots/templates: `SLOT = (SEMANTIC_REFERENCE, ?SLOT_IS_VALUE_OF, ?SLOT_CHILDREN)`; `SEMANTIC_LINK = (SEMANTIC_REFERENCE, REPLACEMENT_VALUE)`; `SEMANTIC_MAP` = `+SEMANTIC_LINK`; `PROTOCOL_DEFAULTS` is also a SEMANTIC_LINKS; `TEMPLATE_SIGNATURE = (*EXPECTED_SLOT)` in process signatures. VM instructions `FILL` ("fill template from map") and `FILL_FROM_MATCH`. — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)
- The abstract REQUESTING protocol (SYS): `(PROTOCOL_DEFINITION (PROTOCOL_LABEL (ENGLISH_LABEL:REQUESTING)) (PROTOCOL_SEMANTICS (ROLE:REQUESTER) (ROLE:RESPONDER) (GOAL:RESPONSE_HANDLER) (GOAL:REQUEST_HANDLER) (USAGE:CHANNEL) (USAGE:REQUEST_TYPE) (USAGE:RESPONSE_TYPE) (USAGE:RESPONSE_HANDLER_PARAMETERS)) (PROTOCOL_DEFAULTS ...) (backnforth (INITIATE (ROLE:REQUESTER) (DESTINATION (ROLE:RESPONDER)) (ACTION:send_request)) (EXPECT (ROLE:RESPONDER) (SOURCE (ROLE:REQUESTER)) (PATTERN (SEMTREX_SYMBOL_LITERAL (SLOT (USAGE:REQUEST_TYPE) (SLOT_IS_VALUE_OF:SEMTREX_SYMBOL)))) (ACTION:send_response))))`. - Unresolved design question left in the source: "how did it get made explicit that the signature of the RESPONSE_HANDLER is of type RESPONSE_TYPE? ... ### Inferences
- "Pluggable" operationally = late binding of (a) which receptor plays which role, (b) which process handles which goal, (c) which concrete symbol fills which usage, (d) which sub-protocol fills which weal — all expressed as data (RESOLUTION trees) so that a protocol can be shipped as an abstract template and instantiated per receptor. The CONNECTION slot type from the design docs is not a symbol in `base_defs`; in code its role is taken by carrier + aspect + address.
- "Wrapping" (INCLUSION) is protocol inheritance by renaming/resolving references; unwrapping is a compile-time (express-time) macro expansion that yields a flat protocol plus a semantic map carried into every expectation and run-tree.

### Gaps
- No implementation of the described "transformational maps", nor of SMTP/FTP front-end protocols; only HTTP request-line parsing and response rendering exist (see Q6).
- Protocol versioning/negotiation ("if they don't recognize a protocol, they can install it and continue processing" — Revelation) is not implemented.

## Key Question 5: What is a scape and what role did it play?

### Takeaway
On paper, scapes are the "relational landscape" that indexes and relates instances (the proposed replacement for tables/RDF, with geometries like list, map, tree, lat/long and a future "scape algebra"). In code, a scape is a minimal hash index: `Scape {Symbol key_source; Symbol data_source; hash(key-tree) → Xaddr}` with `_s_new/_s_add/_s_get`, used by the VMHost to track installed receptors; `SCAPES` is reserved as a section of every DEFINITIONS tree.

### Cited Findings
- Exact C definition: "A scape provides indexed, i.e. random access to data sources. The key source is usually a sub-portion of a the data source, i.e. if the data source is a PROFILE the key_source might be a FIRST_NAME within the profile"; `typedef struct Scape { Symbol key_source; Symbol data_source; ScapeData data; /*uthash*/ }`; `scape_elem {TreeHash key; Xaddr value}`. — [ceptr_types.h](https://github.com/zippy/ceptr/blob/master/src/ceptr_types.h)
- API: `Scape *_s_new(Symbol key_source, Symbol data_source); void _s_add(Scape*, TreeHash, Xaddr); Xaddr _s_get(Scape*, TreeHash);` "scapes organized and relate receptor contents". `_s_add` raises "allready there!" on duplicate keys. — [scape.h](https://github.com/zippy/ceptr/blob/master/src/scape.h), [scape.c](https://github.com/zippy/ceptr/blob/master/src/scape.c)
- Test: `_s_new(TEST_INT_SYMBOL, TEST_STR_SYMBOL)`; add `_t_hash(G_sem, (TEST_INT_SYMBOL:31415))` → Xaddr `{1,3}`; a different symbol hash returns the null Xaddr. — [scape_spec.h](https://github.com/zippy/ceptr/blob/master/spec/scape_spec.h)
- Definitions tree reserves `SCAPES` (`Symbol: SCAPES,[*%SCAPE]`, `Structure: SCAPE,NULL_SYMBOL`, `Symbol: SCAPE_SPEC,NULL_STRUCTURE; @todo...`, `TEST_ALPHABETIZE_SCAPE_SYMBOL,SCAPE`), and trees can carry scapes as surfaces (`TFLAG_SURFACE_IS_SCAPE`, `_t_new_scape`). — [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs), [tree.h](https://github.com/zippy/ceptr/blob/master/src/tree.h)
- Use: `VMHost.installed_receptors` is a `Scape*` keyed by `_t_hash` of a package's `RECEPTOR_IDENTIFIER`, to "make sure we aren't re-installing an already installed receptor". — [vmhost.h](https://github.com/zippy/ceptr/blob/master/src/vmhost.h), [vmhost.c](https://github.com/zippy/ceptr/blob/master/src/vmhost.c)
- Design: Scapes "manage collections of data elements and encode the relationships and dimensions of variability between them. Data is stored as atomic elements, not in SQL tables"; contrasted with RDF triples "which it says make arbitrary assertions rather than defining the ranges that matter"; geometries listed: "sequence, list, map, hash, array, tuple, tree, and enum, plus set membership and lat/long"; "'Scape algebra' (crossing, intersecting, and blending scapes) is proposed but not specified." — [ceptr.org/whitepapers/revelation](http://ceptr.org/whitepapers/revelation)
- Grammatics: scapes = "relational landscape/fabric (between/among instances)". Slide deck: "Scape data (index collections, compute relationships)". — [ceptr.org/whitepapers/grammatics](http://ceptr.org/whitepapers/grammatics), [Prezi](https://prezi.com/y_7109dt0gzj/just-a-spoonful-of-ceptr/)
- Related idea in the codebase: the accumulator exposes `_a_gen_token`, `_a_add_dependency`, `_a_delete_dependency` (instance tokens with dependency tracking, `DEPENDENCY_HASH`, `TOKEN_XADDR`). — [accumulator.h](https://github.com/zippy/ceptr/blob/master/src/accumulator.h), [base_defs](https://github.com/zippy/ceptr/blob/master/src/base_defs)

### Inferences
- Scapes were meant to be the receptor's query/index layer (the "data engine" the VM is "wed to" per the slides), and later ideas such as Holochain's DHT "sharded into hashed segments" descend from the same notion; in this codebase they never grew beyond a single hash map.

### Gaps
- No scape-based query instruction exists in the VM (no `SCAPE_GET`-style process); the `ITERATE_ON_SYMBOL` iteration over instances is the only collection traversal.

## Key Question 6: What was the Ceptr VM / VMHost, and how does it execute processes? (incl. instruction set, run trees, streams, clock/shell/edge receptors, end-to-end signal flow)

### Takeaway
The VMHost is a per-machine host process that owns the SemTable, a routing table of receptors, an active-receptor list, and a main thread that round-robins over active receptors, reducing each receptor's process queue and delivering its pending signals. Execution is tree reduction: a process is instantiated as a `RUN_TREE = (CODE, PARAMS, ?error-CODE, ?error-PARAMS)`; a stepper walks the code tree (Descend/Ascend/Eval/Pushed/Pop/Block states), replaces `PARAM_REF`/`SIGNAL_REF` paths with values, reduces system instructions in place, and pushes a new context for user-defined processes. The ~55 implemented system instructions include definition, instance, control-flow, signaling, conversation, stream, string and integer ops.

### Inferences
- The VM is a tree-rewriting interpreter with explicit continuations (contexts linked by caller/callee), cooperative scheduling per receptor, and blocking primitives (REQUEST without callback, LISTEN without action, STREAM_READ) implemented by moving a context to `Q.blocked` and waking it via `WAKEUP_REFERENCE` (process id + code path). This is the concrete meaning of "parallel tree processing" / "self-reducing trees".
- "Carrier" in the implementation is just a Symbol in the HEAD that expectations filter on first (before Semtrex), and in protocol-generated expectations the interaction name is used as the carrier; the "carrier as medium" language (hormone/lock-and-key analogy) is conceptual.

### Gaps
- "Scenes" — no symbol, struct, or doc mention of "scene(s)" was found anywhere in the codebase, doxygen docs, or ceptr.org pages fetched; I could not confirm this term is a Ceptr concept.
- Threading is minimal (one VM thread, one clock thread, stream reader threads); the "thread pool manager" is a comment.
- "Edge receptors (TCP, socket)": only a generic socket listener + unix FILE streams exist; no distinct TCP/UDP receptor types.
